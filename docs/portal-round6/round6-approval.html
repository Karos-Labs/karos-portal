Eight areas, one page each at most. Every item says where the current build breaks, what we would change, and roughly how big the job is. Nothing here is built yet. You approve, then it ships on its own branch to prep.

01 · Portal-wide

One interaction logic for every card, row and button

S primitives · M sweep

Where it breaks

  • The shared primitives are the root cause. Every Card tints its border and lifts on hover, so static boxes look pressable. Buttons jump 2px and bloom a shadow. The focus ring fails contrast, and inputs remove the browser's, so a keyboard user cannot see the field they are in.
  • On Home the KPI cells are links; the two "SEO & AI visibility" cells beside them are static but wear the identical shell. That is the mismatch you saw.
  • Eleven orange things on Home (icon chips, meter fills, sparkline, a takeaway band, the bell), so the one orange button does not read as the one.
  • Agents surfaces use four row patterns for one meaning. Arrows follow button labels in six places. Run-history rows are boxed like links but do nothing.

What we change

  • Three kinds of thing, three looks. A link: the whole surface is the target, one fill step on hover, one trailing chevron. A button: colour change only, no lift, no shadow; orange on at most one control per screen, the one that moves the client forward. Static: no border tint, no hover, no chevron, or it drops the box and sits on a divider.
  • One focus ring, ink, 2px, on every interactive element including inputs. The seven ring recipes go.
  • Fix the four primitives (Card, Button, Input, TabButton) once; then sweep Home, Agents and Reporting surface by surface. The SEO cells become links into the matching section of the report.
  • Orange on Home becomes exactly: the ladder's button, its progress fill, row hovers, the bell badge. Meters, sparklines and icon chips go ink.
Why this first. Fixing the primitives fixes most of the portal in one commit, and every later item in this document is built on these three looks. Note the primitives are shared with the staff app, so staff pages calm down too.
02 · Home

Get set up: tailored steps that know what is done

M

Where it breaks

  • Only the current step has a control; four of six rows are not clickable at all. "Let's do this" is one label for six different actions and predicts nothing.
  • "Complete your profile" checks description and category, but onboarding already writes category, so the step really means "description missing" and never says so. Clicking lands on Profile with nothing pointed at; if an AI brief exists the profile even looks complete.
  • "Confirm your brand voice" ticks the moment a document is opened. "Set up your first agent" cannot tell "form saved" from "stand-up run missing". "Run your first agent" counts failed runs. "See your first result" counts an asset existing, not the client opening it.
  • The waiting row ("Karos is setting up your agent") has no horizon and can be wrong while posts already arrive daily. A finished checklist comes back every 7 days.

What we change

  • Every incomplete row is a link to its own landing with a status word at the right ("Not started", "After step 3"). Only the current row carries the orange button. Done rows go plain.
  • The button names the action and the missing thing: Add a short description · Read your Target Audience · Add your LinkedIn agent details · Create your first Instagram post · Open your first post. The line under the current row says what is already done.
  • Each landing shows a small "You're here to add a short description" band with the target field outlined and focused. It clears on the first save.
  • Honest signals per step: Profile = category, description and website, each named. Voice = each document read and marked "Looks right". Agent = details saved and stand-up done, or live by evidence. Run = one run reached review or delivered. Result = the client opened a post.
  • On completion: "You're set up. Your agents are running." and one Done. The card does not come back.
03 · Agent page

Status that matches reality ("Runs on request" while posting daily)

S predicate · M model

Where it breaks

  • The bug. Imported posts are saved as drafts. The one-post-a-day chain only ever moves drafts onto future days, so every future day of the stream is a draft by construction. The "Live" check counts scheduled posts and explicitly rejects drafts, using a rule from before clients could see drafts. So the calendar shows a planned week while the agent above it says "Runs on request", and its aside adds "No schedule yet".
  • The status word is printed twice: a mono chip beside the logo and a tinted strip 100px lower, in two typographic voices. The strip can only say "Last delivered" and "In your Workspace", nothing about what comes next, the one question a client of a daily stream has.
  • Staff and client can read different words for the same agent ("Live" versus "Needs attention"), which breaks parity. Home's checklist uses its own flag for "live", so it can disagree with the agent page.

What we change

  • Fix the predicate: upcoming counts client-visible drafts, 14-day window. Your agent reads Live the day it ships. The checklist reads the same function, so Home and the agent page cannot disagree.
  • The status words stay as they are; they were never the problem. One badge component renders them on the roster, the agent page and Reporting. The reason becomes a sentence under the badge ("Your LinkedIn details are missing"), never a new word. A failed run becomes an Internal marker for staff, so both viewers read the same word.
  • The chip beside the logo goes. The strip becomes one plain line under the title; each fact with a destination is a link, "Adjust pace" sits at the end when a schedule exists:
● Live · Next post Thu 5 · 7 posts planned · Last delivered Aug 4 · 12 in your Workspace Adjust pace
04 · Bell

Notifications with one logic: every row opens something

S now · M phase 2

Where it breaks

  • "2 unread" is a static chip, and a second number beside the badge's.
  • The client's rows are Karos-owned states ("Your Karos team is reviewing new work", "Tasks are in progress"): inert, and counted in the badge.
  • The events a client actually waits for, a post landing or a run finishing, produce no notification at all.

What we change

  • The rule. A row is one event or condition the client can open or act on, with one destination. Otherwise it is not a row and not counted; it stays an indicator on Home. The badge equals the rows in the panel, always.
  • This round. The Karos-owned rows go for clients. Meeting action items become whole-row links with "Done" as a separate control. "N unread" becomes a quiet "Mark all as read". The empty state says "Nothing needs you right now." with a link to the calendar.
  • Phase 2, a later round. The rows a client actually waits for: Your Instagram post is ready (opens the post) · 1 post did not go out (opens the day) · LinkedIn needs reconnecting (opens settings) · 3 posts are waiting to be marked as posted (opens the calendar). Needs one URL key to open a single post, which the checklist's last step needs anyway.
05 · Agent page

Create a post: one question, one calm footer

M

Where it breaks

  • Operator vocabulary above the fold ("Social content system. Choose whether to set up, refresh, or produce..."), then six fields in a grid with a red asterisk. "What should the agent do?" offers staff operations to a client.
  • The dashed "No reference files are available" box is a dead control: clients cannot upload, the route refuses them.
  • The footer is a bordered band with a clock icon, two sentences, the price and an orange "Start run" that wraps onto two lines. The trigger said "Create a new post".
  • The price says "about 25 credits" whether the client asks for 1 post or 10, because post count is not the charge multiplier.

What we change

  • One required field, three "Try:" chips that fill it. Defaults as one muted line with Change. One "More options" disclosure holds channel, count, audience, must include or avoid. The staff-only run types (set up, refresh) stay inside the staff block. Files: nothing renders for clients, staff keep their picker.
  • Title and button say Create post (clip or reply for other agents). The confirm is paper; the page's own run button keeps the one orange. Default count 1 and the price follows the count, so the quoted price is the price.

06 · Navigation and Agents tab

Sidebar without stars; a roster you can compare

S rail · M roster

Where it breaks

  • Every rail row carries a star. Unpinned ones are grey glyphs with no meaning until hovered; pinned ones are orange, so four pins spend the accent four times in the nav. The parent "AI agents" row and the child row both read as current.
  • The Agents tab is a two-column card grid where a Live Instagram agent and a never-run Reddit agent are the same rectangle. No "last made", no "next", no verb.
  • Not set up yet: a placeholder video frame reading "coming soon", or an empty state promising "They will let you know", which no code does.

What we change

  • Rail rows: platform mark and name, nothing else, 32px tall, identical to the other nav rows (which are already right and only gain the focus ring). Pinned first, hairline, then the rest capped at 6 with "View all". One current row per rail.
  • Pinning lives on the agent page only, ink not orange. Research behind this: NN/g vertical navigation, Apple HIG sidebars, Material navigation drawer, GitHub Primer NavList. All four keep trailing actions off row defaults.
  • Roster: one row per agent, the whole row a link (below).
  • Not-set-up pages get a real action and honest copy: "Not set up yet. Your Karos team sets this up. Tell us when you want it." No video frame without a video.

07 · Reporting

What we are doing, and things only you can do

S + M

Where it breaks

  • Whether a finding is "yours" is read off where the check sits in the scoring table, not off who can act on it. That is how three outcomes our agents exist to move (share of voice, named-mention rate, never cited) became client tasks: "Get your name in front of buyers", "Get quoted where the engines are already looking", "Catch up with the competitor leading these answers".
  • The section sits second on the tab, straight under the scores.
  • The only "what Karos does" pointer on the tab is one hand-built Reputation card. Nothing connects the scores to the agents that move them. The takeaway line says "the work below closes the gap" on Home, where there is no work below.

What we change

  • Things only you can do becomes an explicit allow-list of three, everything else is dropped: Claim your public company record · Point your public record at your own website · Open your listings on the review platforms. Each keeps the measured evidence line. Empty state: "Nothing on your side is holding you back right now." It moves to the very bottom.
  • New section under the scores: What we are doing to improve your SEO and GEO. One row per agent: mark, name, one honest sentence on the lever it moves, the same status badge as the Agents tab, and one outline button Open Reddit Agent straight to its page. Agents not on the plan read "Not on your plan" with Support (a client cannot open a page for an agent they do not have).

10 · After approval

How it would ship

Order of work, each its own PR to prep

  1. Primitives and the status predicate. Two small fixes with the biggest visible effect: the whole portal calms down and your agent reads Live.
  2. Reporting. The three-item allow-list, the new agents section, the order, Seats out.
  3. Status and Agents tab. One badge everywhere, one line under the title, rows instead of cards, the rail without stars.
  4. Get set up. Per-step detection, named buttons, landings with the field outlined.
  5. Create a post. The one-question dialog.
  6. Notifications. The clean-up. The client feed waits for a later round.

Guardrails

  • Executors on Opus 5; every logic, copy and status decision on Fable 5.1; a risk agent reads every PR against your rulings before merge.
  • Same page for staff and clients; staff extras only as marked Internal blocks. One orange per screen. No em dashes in client copy (a test enforces it). Prices read "about N credits".
  • Merges land on prep only. Production stays on the manual promote. The credits flag stays off in production.
  • Two risks we manage: the shared primitives also change hover and focus on staff pages, so that PR gets its own sweep of the admin pages; and widening "live" flips the status of every client with imported future drafts at once, so we check each client's attribution first.
  • Not in this round, still your open calls: brand-voice editing by the client, self-serve credit top-up, calendar "Schedule a run" for clients (stays staff only), and asking clients for site or Search Console access as a structural item (needs a new data field).

Decided without you, say if you disagree: no client uploads in the dialog (the route refuses them on purpose); no renaming of status words; the general "get named on other sites" item is out; Support stays the one word for every help trigger; dynamic agents are not in the Reporting section yet; asking clients for site access waits for a data field; the Karos-owned rows leave the client's bell.
